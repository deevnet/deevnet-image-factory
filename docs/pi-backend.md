# Pi Take-Home Backend Image Build

This document covers building the `pi-backend` image: a mini Deevnet on an SD card that a tenant
takes home after prototyping on Deevnet.

## Overview

At a meetup, a tenant builds its app against Deevnet: the broker at `mqtt.mobile.deevnet.net:8883`,
the log store at `:8427`, its topics under `<tenant>/`. This image lets it move that app to a
Raspberry Pi of its own and keep the same **app contract**:

| Service | On the Pi | On Deevnet |
|---------|-----------|------------|
| MQTT, TLS only, `:8883` | Mosquitto 2.0.11 (Debian) | VerneMQ |
| Log store | VictoriaLogs, loopback only | VictoriaLogs |
| Log front door, TLS, `:8427` | vmauth, users rendered by `deevnet-log-user` | the same |
| Device logs | `deevnet-log-bridge`, `+/log/#` → the tenant's `(index, 2)` | the same binary |
| Dashboards, HTTPS, `:3000` | Grafana 13.2.2 with the VictoriaLogs plugin; organisation, login and data sources by `deevnet-kit dashboards` | the same Grafana, written by the API (CHG-0024) |
| Accounts, first boot, status | `deevnet-kit` | the Deevnet API |
| The tenant's app | Podman (4.3: no quadlets; an example unit is included) | a workload VM |
| Name | `<hostname>.local` (avahi) | site DNS |

There is **no Deevnet API, Terraform, DNS, Wi-Fi key or workload VM** on the Pi.

**Nothing secret is baked in.** The CA, server certificate, log tokens, bridge credentials and
Grafana's admin password, secret key and tenant login are generated by `deevnet-kit init` on the
card's first boot, so no two cards share anything.

**Dashboards follow Deevnet's contract.** `deevnet-kit dashboards` uses the API's own Grafana client
(`internal/backend/grafana`), so the tenant gets the same organisation, Editor login and three log
data sources with the same fixed UIDs (`deevnet-logs-workloads`, `-platform`, `-devices`). A
dashboard written against Deevnet applies here unchanged. It runs from its own unit after Grafana
and vmauth, on every boot, because `init` runs before any service starts.

**Nothing of Deevnet's stays.** The shared Packer step adds `a_autoprov`; `pi-backend-config`
removes the user, its home and its sudo rule, then fails the build if any trace is left. The
owner's login and Wi-Fi come from Raspberry Pi Imager's OS customisation.

## Inputs

All arm64, all from the artifact server, fetched into `build/pi-backend/` by `make pi-backend-inputs`:

| Binary | Staged by |
|--------|-----------|
| `deevnet-kit`, `deevnet-log-user` | `deevnet-provisioning-api`: `make stage-pi` |
| `deevnet-log-bridge` | `deevnet-log-bridge`: `make stage-pi` |
| `victoria-logs-prod`, `vmauth-prod` | this repo: `make pi-backend-stage-upstream` (once per version) |
| `grafana.tar.gz` (Grafana's linux-arm64 release) | this repo: `make pi-backend-stage-upstream` |
| `grafana-plugin.zip` (VictoriaLogs data source) | `deevnet.builder` artifacts (`--tags fetched-artifacts`), the zip Deevnet's Grafana uses |

The VictoriaLogs, vmauth and Grafana versions are pinned to the ones Deevnet runs, with the release
checksums in the Makefile. Every staging target refuses a dirty tree or a bad checksum. The plugin
zip carries every platform's backend, and all of them are kept: the plugin's signed manifest lists
every file, and a missing one fails the signature check.

## Build Process

```bash
# Once per version bump, on the Builder
make pi-backend-stage-upstream
(cd ../deevnet-provisioning-api && make stage-pi)
(cd ../deevnet-log-bridge && make stage-pi)

# Full pipeline: inputs -> base image -> resize -> config -> compress
make pi-backend
```

The build pipeline:
1. **pi-backend-inputs**: fetches the five binaries and checks they are arm64, then Grafana and the
   plugin, checked by sha256
2. **pi-bookworm-image-backend**: base Bookworm image (the shared Packer template)
3. **pi-resize-image-backend**: expands the image to 8GB
4. **pi-backend-config**: offline Ansible in a chroot (`ansible/playbooks/pi-backend-config.yml`)
5. **pi-compress-image-backend**: compresses with xz for Pi Imager

Output: `raspios-bookworm-mobile-pi-backend.img.xz`.

## First Boot

1. Flash with Raspberry Pi Imager. In OS customisation set the hostname, user, Wi-Fi, and enable SSH.
2. Before ejecting, edit `deevnet-kit.txt` on the boot partition: `tenant=` and `index=` as on
   Deevnet (`terraform output`). Left empty, the tenant is `pi`, index 1.
3. Boot. Imager's own first boot runs and reboots. Then `deevnet-kit-firstboot.service` runs once
   and the services start.
4. `sudo deevnet-kit status`, then `sudo deevnet-kit export ~/deevnet-kit` for `kit.env` and
   `site-ca.pem`.

## Where Things Live on the Card

| Path | What |
|------|------|
| `/boot/firmware/deevnet-kit.txt` | tenant and index, read once |
| `/etc/deevnet-kit/kit.json` | the tenant and its tokens (root, 0600). Its presence means first boot ran |
| `/etc/deevnet-kit/accounts/` | one file per broker account (hash, never the password) |
| `/etc/deevnet-kit/tls/` | the card's CA and the server certificate |
| `/etc/mosquitto/deevnet-kit/{passwd,acl}` | rendered by `deevnet-kit`; do not edit |
| `/etc/deevnet-kit/log/` | `deevnet-log-user`'s inputs and vmauth's `auth.yml` |
| `/etc/deevnet-kit/grafana.env` | Grafana's admin password and secret key (root, 0600) |
| `/opt/grafana`, `/var/lib/grafana-plugins` | Grafana and the plugin, root-owned and read-only to the service |
| `/var/lib/grafana` | Grafana's database |
| `/opt/deevnet-kit/examples/my-app.service` | a unit that runs the tenant's app container |

## Memory

Grafana wants about 512 MB on top of the rest. A Pi 4 or 5 is the comfortable choice. On a
512 MB Zero 2 W, turn the dashboards off and read logs by query:
`sudo systemctl disable --now grafana deevnet-kit-dashboards`.

## Known Differences from Deevnet

- **A refused subscription is not refused.** VerneMQ answers a subscribe outside the account's
  grant with a failure in the SUBACK. Mosquitto 2.0.11 grants it and then delivers nothing. Either
  way no message crosses; an app that checks the SUBACK sees a difference.
- **One tenant.** The Pi's owner is also its operator, and holds Grafana's admin login
  (`grafana_admin_password` in `/etc/deevnet-kit/kit.json`).
- **No device registry.** A device account names its device; the name is checked for shape only.
- **Revocation is immediate.** `deevnet-kit account rm` reloads Mosquitto, and 2.0.11 disconnects a
  connected client whose account is gone (tested against Debian's package). On Deevnet a revocation
  takes effect on the client's next connect.
