# Pi Take-Home Backend Image Build

This document covers building the `pi-backend` image: a mini Deevnet on an SD card that a tenant
takes home after prototyping on Deevnet.

**The backend's tool is `tenant2backend`, and its files take the noun `backend`** (ADR-0045,
CHG-0078). Before v0.28.0 it was `deevnet-kit`, with `/etc/deevnet-kit` and the rest: an image
built earlier keeps those names. For one release the image keeps `/usr/local/bin/deevnet-kit` as a
link, which says the new name when called, and first boot reads a card's `deevnet-kit.txt` when
`backend.txt` holds no setting. The app contract keeps Deevnet's names.

## Overview

At a meetup, a tenant builds its app against Deevnet: the broker at `mqtt.mobile.deevnet.net:8883`,
the log store at `:8427`, its topics under `<tenant>/`. This image lets it move that app to a
Raspberry Pi of its own and keep the same **app contract**:

| Service | On the Pi | On Deevnet |
|---------|-----------|------------|
| MQTT, TLS only, `:8883` | Mosquitto 2.0.11 (Debian) | VerneMQ |
| Log store | VictoriaLogs, loopback only | VictoriaLogs |
| Log front door, TLS, `:8427` | vmauth, users rendered by `deevnet-log-user` | the same |
| Device logs | `deevnet-log-bridge`, `+/log/#` → the tenant's `(index, 2)` | the same binary |
| Dashboards, HTTPS, `:3000` | Grafana 13.2.2 with the VictoriaLogs plugin; organization, login and data sources by `tenant2backend dashboards` | the same Grafana, written by the API (CHG-0024) |
| Metrics, TLS, `:8427` | the VictoriaMetrics cluster (vmstorage, vminsert, vmselect `v1.156.0-cluster`), loopback only, behind the same vmauth; routes rendered by `deevnet-log-user` | the same store and routes (CHG-0070) |
| Alert rules | `vmalert@<tenant>`, rules imported with `tenant2backend alerts import` from the tenant's Terraform | `deevnet_alert_rule_group`, through the API (CHG-0071) |
| Alerts to the phone, TLS, `:443` | Alertmanager `v0.35.0` and ntfy `v2.38.0`; the phone on the Pi's network | the same, on site |
| Buckets, TLS, `:9000` | silo, cross-built for arm64 from the same tag; off until `tenant2backend bucket add` | silo (CHG-0069) |
| Accounts, first boot, status | `tenant2backend` | the Deevnet API |
| A PKI of the owner's own | `deevnet-pki-owner.sh`, run by `tenant2backend pki`; `cryptsetup` for the root key's stick | the Deevnet Root and the tenant CAs |
| The tenant's app | Podman (4.3: no quadlets; an example unit is included) | a workload VM |
| Name | `<hostname>.local` (avahi) | site DNS |

There is **no Deevnet API, Terraform, DNS, Wi-Fi key or workload VM** on the Pi.

**Nothing secret is baked in.** The CA, server certificate, log tokens, bridge credentials and
Grafana's admin password, secret key and tenant login are generated by `tenant2backend init` on the
card's first boot, so no two cards share anything.

**Dashboards follow Deevnet's contract.** `tenant2backend dashboards` uses the API's own Grafana client
(`internal/backend/grafana`), so the tenant gets the same organization, Editor login and three log
data sources with the same fixed UIDs (`deevnet-logs-workloads`, `-platform`, `-devices`). A
dashboard written against Deevnet applies here unchanged. It runs from its own unit after Grafana
and vmauth, on every boot, because `init` runs before any service starts.

**Nothing of Deevnet's stays.** The shared Packer step adds `a_autoprov`; `pi-backend-config`
removes the user, its home and its sudo rule, then fails the build if any trace is left. It also
deletes the SSH host keys the image was built with; `backend-ssh-hostkeys.service` makes the
card's own on first boot, so no two cards present the same SSH identity.

**The owner sets the card up on its boot partition.** Imager 2.x offers no OS customization for a
custom image, so the owner's login is `userconf.txt`, SSH is an empty `ssh` file, and the host
name and Wi-Fi are `hostname=` and `wifi_*=` in `backend.txt`, which `tenant2backend init`
applies before it issues the server certificate.

## Inputs

All arm64, all from the artifact server, fetched into `build/pi-backend/` by `make pi-backend-inputs`:

| Binary | Staged by |
|--------|-----------|
| `tenant2backend`, `deevnet-log-user` | `deevnet-provisioning-api`: `make stage-pi` |
| `deevnet-pki-owner.sh`, `deevnet-pki-media.sh`, `deevnet-pki-owner.cnf` | the `ansible-collection-deevnet.mgmt` checkout beside this one (`scripts/pki`), recorded by commit in `/usr/local/share/deevnet-pki/RELEASE` |
| `deevnet-log-bridge` | `deevnet-log-bridge`: `make stage-pi` |
| `victoria-logs-prod`, `vmauth-prod` | this repo: `make pi-backend-stage-upstream` (once per version) |
| `grafana.tar.gz` (Grafana's linux-arm64 release) | this repo: `make pi-backend-stage-upstream` |
| `grafana-plugin.zip` (VictoriaLogs data source) | `deevnet.builder` artifacts (`--tags fetched-artifacts`), the zip Deevnet's Grafana uses |

The VictoriaLogs, vmauth and Grafana versions are pinned to the ones Deevnet runs, with the release
checksums in the Makefile. Every staging target refuses a dirty tree or a bad checksum. The plugin
zip carries every platform's backend, and all of them are kept: the plugin's signed manifest lists
every file, and a missing one fails the signature check.

## Build Process

```bash
# Once per version bump, on the Builder
make pi-backend-stage-upstream
(cd ../deevnet-provisioning-api && make stage-pi)
(cd ../deevnet-log-bridge && make stage-pi)

# Full pipeline: inputs -> base image -> resize -> config -> compress
make pi-backend
```

The build pipeline:
1. **pi-backend-inputs**: fetches the five binaries and checks they are arm64, then Grafana and the
   plugin, checked by sha256
2. **pi-bookworm-image-backend**: base Bookworm image (the shared Packer template)
3. **pi-resize-image-backend**: expands the image to 8GB
4. **pi-backend-config**: offline Ansible in a chroot (`ansible/playbooks/pi-backend-config.yml`)
5. **pi-compress-image-backend**: compresses with xz for Pi Imager

Output: `raspios-bookworm-mobile-pi-backend.img.xz`.

## First Boot

1. Flash with Raspberry Pi Imager, choosing the image as a custom file.
2. Before ejecting, on the boot partition:
   - `backend.txt`: `tenant=` and `index=` as on Deevnet (`terraform output`; left empty,
     the tenant is `pi`, index 1), `hostname=`, and `wifi_ssid=`, `wifi_psk=`, `wifi_country=`
     when not on a cable;
   - `userconf.txt`: `user:$(openssl passwd -6)`;
   - an empty `ssh`.
3. Boot. Raspberry Pi OS creates the user, grows the filesystem and reboots. Then
   `backend-firstboot.service` runs once: host name, Wi-Fi (its password then blanked on the
   boot partition), CA, certificate, tokens, and the services start.
4. `sudo tenant2backend status`, then `sudo tenant2backend export ~/backend` for `kit.env` and
   `backend-ca.pem`.

**A card never starts before the day its image was built.** A Pi has no clock battery, and
`fake-hwclock` restores the build's time on a new card. First boot and Grafana then wait for NTP
(`systemd-time-wait-sync`) for 90 seconds at most: the card's CA and certificate start today, and
Grafana checks its plugins' signatures against a clock that is right. With no NTP server in reach,
they start 90 seconds later on the restored time.

`README.txt` sits beside `backend.txt` on the boot partition, so the owner can read the
instructions on a laptop before the first boot, and again at `/opt/backend/README.txt`. The
login message (`/etc/motd`) points there.

## Self-Test

`sudo tenant2backend selftest` proves the card end to end, as an app and a device use it:
1. the services (one the owner disabled is reported off, not failed);
2. TLS on 8883, 8427, 3000 and 443 against the card's CA;
3. the bridge's subscription;
4. a device log line published over MQTT through a throwaway account, read back from `<index>-2`;
5. an app line sent with the ingest token, read back from `<index>-0`;
6. a metric pushed with the ingest token and found with the read token, and another tenant's
   partition refused;
7. as the tenant's Grafana login: Editor in one organization, the log and metrics data sources,
   the starter dashboard, and the device line read back through Grafana;
8. Alertmanager ready; the phone's ntfy login reads its own topics and publishes nowhere; and,
   once rule groups are loaded, `vmalert@<tenant>` evaluating each with no error.

`backend-selftest.service` runs it after every boot; `tenant2backend status` shows the last
result, and a failure is also a failed unit. Each run leaves two log lines marked
`tenant2backend selftest`, which age out with retention.

`tenant2backend dashboards` also creates a **"Start here"** dashboard (temperature from device logs,
device logs, app logs) when none has its UID. It never overwrites it: once created, it is the
owner's.

## Where Things Live on the Card

| Path | What |
|------|------|
| `/boot/firmware/backend.txt` | tenant and index, read once |
| `/etc/backend/kit.json` | the tenant and its tokens (root, 0600). Its presence means first boot ran |
| `/etc/backend/accounts/` | one file per broker account (hash, never the password) |
| `/etc/backend/tls/` | the CA the services trust and the server certificate |
| `/etc/backend/owner-ca/` | the owner's issuing CA and root certificate, after `tenant2backend pki init`. The root's key is on the owner's stick, never here |
| `/usr/local/sbin/deevnet-pki-owner.sh`, `/usr/local/share/deevnet-pki/` | the starter PKI's tools and profile |
| `/etc/mosquitto/backend/{passwd,acl}` | rendered by `tenant2backend`; do not edit |
| `/etc/backend/log/` | `deevnet-log-user`'s inputs and vmauth's `auth.yml` |
| `/etc/backend/grafana.env` | Grafana's admin password and secret key (root, 0600) |
| `/etc/backend/alerts.json` | the rule groups `tenant2backend alerts import` loaded |
| `/etc/backend/alerting/` | Alertmanager's routes and ntfy's users (by `deevnet-log-user`), the publisher's password |
| `/var/lib/backend/vmalert/<tenant>/` | the tenant's vmalert: rules, read token, port; watched by `deevnet-alerting-sync.path` |
| `/var/lib/vmstorage` | the metrics, 30 days |
| `/etc/backend/buckets/` | each bucket's settings and keys (root, 0600) |
| `/etc/backend/silo.env`, `/var/lib/silo` | silo's root login, made with the first bucket, and the objects |
| `/opt/grafana`, `/var/lib/grafana-plugins` | Grafana and the plugin, root-owned and read-only to the service |
| `/var/lib/grafana` | Grafana's database |
| `/var/lib/backend/selftest.json` | the last self-test's result |
| `/boot/firmware/README.txt`, `/opt/backend/README.txt` | the owner's instructions |
| `/opt/backend/examples/my-app.service` | a unit that runs the tenant's app container |

## Memory

Grafana wants about 512 MB on top of the rest. The metrics store and alerting add at most about
370 MB, as measured under emulation on the Builder (CHG-0072, Step 2), which overstates a real
Pi; each unit also has a `MemoryMax`. A Pi 4 or 5 with 2 GB or more is the comfortable
choice. On a 1 GB Pi, the full set fits without much room for the app. On a 512 MB Zero 2 W, run
MQTT and logs only:
`sudo systemctl disable --now grafana backend-dashboards vmstorage vminsert vmselect alertmanager ntfy backend-alerting`.
`status` and `selftest` then report those as off.

## Known Differences from Deevnet

- **A refused subscription is not refused.** VerneMQ answers a subscribe outside the account's
  grant with a failure in the SUBACK. Mosquitto 2.0.11 grants it and then delivers nothing. Either
  way no message crosses; an app that checks the SUBACK sees a difference.
- **One tenant.** The Pi's owner is also its operator, and holds Grafana's admin login
  (`grafana_admin_password` in `/etc/backend/kit.json`).
- **No device registry.** A device account names its device; the name is checked for shape only.
- **Metrics are kept 30 days**, not Deevnet's 90: an SD card is not a data disk.
- **Alerts reach the phone on the Pi's own network only.** Nothing goes to ntfy.sh.
- **Revocation is immediate.** `tenant2backend account rm` reloads Mosquitto, and 2.0.11 disconnects a
  connected client whose account is gone (tested against Debian's package). On Deevnet a revocation
  takes effect on the client's next connect.
